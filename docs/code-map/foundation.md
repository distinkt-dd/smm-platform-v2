# Базовая структура приложений

Backend и frontend — независимые npm-проекты. Исходный состав зависимостей взят из SMM в кармане; Tailwind CSS добавлен отдельно по запросу. Наличие пакета не означает, что его функциональность уже подключена к приложению.

Версии Node.js и npm, а также порядок первого запуска указаны в [режиме локальных проверок](../local-development.md#первый-запуск).

Для совместного запуска в Docker используются `compose.yaml`, `backend/Dockerfile` и `frontend/Dockerfile`; nginx использует `frontend/nginx.conf` для SPA-маршрутов и возвращает 404 для отсутствующих файлов в `/assets/`; сервис `db` запускает PostgreSQL с именованным томом и проверкой готовности. Команды и ожидаемый результат описаны в [режиме локальных проверок](../local-development.md).

## Backend

- Точка входа: `backend/src/main.ts`; стартовый модуль: `backend/src/app.module.ts`.
- Nest CLI, TypeScript, NestJS, `@nestjs/config`, Express и Vitest; установлены также пакеты Prisma/PostgreSQL, авторизации, валидации, почты и обработки файлов из исходного проекта.
- Из `backend`: `npm ci`, `npm run start:dev`, `npm run build`, `npm test`, `npm run test:e2e`, `npm exec --no -- prisma validate` (схема проверяется без запущенной БД и без `DATABASE_URL`).
- `backend/.env.example` описывает локальное окружение. `ConfigModule` загружает `backend/.env` при запуске из каталога backend, а `backend/src/require-database-url.ts` проверяет наличие непустого `DATABASE_URL`; Prisma CLI загружает тот же файл через `backend/prisma.config.ts`. Команды Compose используют этот файл через `--env-file`.
- Схема Prisma задана в `backend/prisma/schema.prisma`, конфигурация — в `backend/prisma.config.ts`; каталог генерации `backend/src/generated/prisma` исключён из Git. Модель `User` хранится в таблице `users`; первая миграция находится в `backend/prisma/migrations`. Применение миграций: `npm exec --no -- prisma migrate deploy` из `backend` при доступной базе. Доступны регистрация, вход с access-токеном и защищённый маршрут текущего пользователя.
- `MasterProfile` связан с `User` один-к-одному; `Service` и `ConfirmedFact` принадлежат профилю и каскадно удаляются вместе с ним. Схема и миграция находятся в `backend/prisma/schema.prisma` и `backend/prisma/migrations`. Проверки схемы: `prisma validate` без `DATABASE_URL`, `prisma generate`, `npm run build`, `prisma migrate deploy` на чистой базе и проверка каскадного удаления.

Готовность базы проверяется только реальным запросом: в режиме driver adapter `$connect()` соединение не открывает, потому что пул `pg` подключается лениво при первом запросе. Поэтому при недоступной базе приложение стартует, пишет ошибку в лог и отвечает `503` на проверку готовности, а падают только запросы к базе.

Пул получает `connectionTimeoutMillis: 5000`: без таймаута запрос к базе, которая принимает TCP-соединение, но не отвечает, ждал бы бесконечно — `GET /health` не вернул бы `503`, а `pool.end()` при остановке не завершился бы.

При остановке приложения соединение закрывается: точка входа `backend/src/main.ts` включает `app.enableShutdownHooks()`, поэтому по `SIGTERM` и `SIGINT` выполняется `onModuleDestroy` с `$disconnect()` и `pool.end()`. В контейнере `backend/Dockerfile` запускает `node dist/main.js` без обёртки npm, чтобы сигнал остановки приходил процессу Node напрямую.

## Frontend

- Точка входа: `frontend/src/main.tsx`; стартовый компонент: `frontend/src/App.tsx`; маршрут `/` ведёт на `HomePage` из `frontend/src/pages`.
- Слои FSD сверху вниз: `pages` → `widgets` → `entities` → `shared`; импорт допустим только вниз. Страницы лежат в `frontend/src/pages`, общие layouts (`AuthLayout`, `MainLayout`) — в `frontend/src/pages/layouts`, самостоятельные блоки интерфейса — в `frontend/src/widgets`.
- Базовый транспорт `frontend/src/shared/api/api.ts` использует `fetch`, обязательный `VITE_API_URL` и `credentials: include`; для изменяющих запросов добавляет `X-CSRF-Protection`. Принимает JSON-тело, заголовки и необязательный Bearer-токен; успешный ответ разбирается как JSON или возвращает `undefined` при пустом теле. Общая функция `requireResponse` проверяет обязательное наличие тела ответа. Защищённые запросы по умолчанию при `401` уведомляют store об истечении сессии; публичные запросы явно задают `protected: false`. Ответ старой сессии не сбрасывает новый вход. HTTP-ошибка содержит статус и сообщения сервера, ошибка сети выделена отдельно; тип ответа задаётся вызывающим кодом и не проверяется во время выполнения. Пути авторизации находятся в `frontend/src/shared/api/endpoints.ts`. Проверки: `npm run build`, `npm run lint`.
- API авторизации `frontend/src/entities/auth/api/auth-api.ts` предоставляет `register`, `login`, `me` и `logout` через общий транспорт; публичные экспорты — `frontend/src/entities/auth/index.ts` и `frontend/src/entities/index.ts`. Типы запросов и ответов находятся в `frontend/src/entities/auth/api/types.ts`, дата `createdAt` в JSON представлена строкой. Перед регистрацией и входом схема `credentials-schema.ts` через Zod и `validator` проверяет правила backend и нормализует email; общая функция `validate` в `frontend/src/shared/lib/validate.ts` возвращает данные либо первые сообщения ошибок по путям полей. При невалидных данных API отклоняет промис с `ValidationError`, содержащей ошибки полей; запрос не отправляется. Для ответов с данными пустой успешный ответ считается ошибкой. Проверка: `npm exec --no -- vitest run`, `npm run build`, `npm run lint`.
- Redux store подключён через `Provider` в `frontend/src/main.tsx`, конфигурация находится в `frontend/src/app/store`; типы `RootState` и `AppDispatch` объявлены глобально, типизированные хуки доступны из `frontend/src/shared/store`. Slice `frontend/src/entities/auth/model/auth-slice.ts` хранит пользователя, состояния и ошибки запросов `login`, `register`, `me`, `logout`; токен хранится только в HttpOnly-cookie backend. При `401` защищённого запроса store очищает пользователя и показывает на странице входа отдельное сообщение; ошибка неверных учётных данных обрабатывается отдельно. При старте запрос `me` восстанавливает пользователя, старый токен `auth.accessToken` удаляется из `localStorage`. Redux DevTools отключены: аргументы auth thunk содержат пароль, middleware также не должны его журналировать. Проверка: `npm exec --no -- vitest run`, `npm run build`, `npm run lint`.
- `FormContainer` в `frontend/src/shared/ui/form-container` задаёт общую ширину и отступы содержимого страниц входа и регистрации; поля и обработка отправки остаются в конкретной форме.
- `LoginForm` и `RegisterForm` используют виджет `frontend/src/widgets/auth-form`: значения полей остаются локальными, отправка идёт через auth thunk, а статусы и ошибки читаются из Redux. Валидация и нормализация выполняются в auth API; ошибки показываются рядом с полями или в конце формы. Общий `Input` связывает ошибку с полем через `aria-describedby` и `aria-invalid`. Проверка: `npm exec --no -- vitest run` (включая формы с подменой `fetch`), `npm run build`, `npm run lint`.
- Каркас страниц: `MainLayout` держит общую шапку `Header` из `frontend/src/widgets/header` (логотип и ссылки на вход и регистрацию, активный маршрут выделен через `NavLink`) и слот `<main>`; `AuthLayout` вложен в него и сужает колонку форм до `max-w-preview`. Маршрут `*` тоже вложен в `MainLayout`, поэтому страница 404 показывается в общем каркасе с шапкой.
- Главная страница `/` защищена компонентом `frontend/src/shared/ui/protected-route`: до завершения `/auth/me` показывает ожидание, гостя перенаправляет на `/login`, а при ошибке сети предлагает повторить проверку. Ответ `401` при восстановлении сессии не уводит гостя со страниц входа и регистрации. В шапке авторизованному пользователю доступен выход.
- React, TypeScript, Vite и Tailwind CSS через `@tailwindcss/vite`; также установлены Redux Toolkit, React Router и инструменты тестирования из исходного проекта.
- Базовые стили и токены дизайн-системы: `frontend/src/index.css` (`@theme` Tailwind CSS v4); отдельного `App.css` нет. Состав токенов и утилит описан в [дизайн-системе](../design-system.md#токены-в-коде).
- Из `frontend`: `npm ci`, `npm run dev`, `npm run build`, `npm run lint`.
- Подключение остальных экранов к backend пока не настроено. Вёрстка опирается на готовые токены.
